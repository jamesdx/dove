# 非功能性需求（NFR）信息模板

> 本文档用于汇总并细化项目在 **性能、可用性、安全合规、可维护性、可观测性、技术约束** 等非功能性方面的关键需求，以便后续在架构设计、开发、测试、运维阶段都能得到明确指导。

---

## 1. 性能需求（Performance Requirements）

- **1.1 并发 & 吞吐量 (QPS / TPS)**  
  - [示例] 系统需支持日均 500 万 DAU，高峰并发 2 万 QPS；  
  - [示例] 订单提交峰值时需保证至少 1000 TPS。

- **1.2 响应时间 (Response Time)**  
  - [示例] 在高峰负载时，95% 请求需在 200ms 内完成；  
  - [示例] 后端接口间调用需维持 < 50ms 的平均耗时。

- **1.3 峰值负载 & 扩展性**  
  - [示例] 系统需能够自动伸缩，在流量激增 3 倍时仍保持可用；  
  - [示例] 数据写入峰值每秒 10 万条日志，应有相应缓存或队列处理。

- **1.4 其他性能关注点**  
  - [示例] 大批量导入/导出时的操作时间限制、批处理耗时等；  
  - [示例] 前端页面首屏加载时间 < 2s。

---

## 2. 可用性需求（Availability Requirements）

- **2.1 SLA (Service Level Agreement)**  
  - [示例] 服务全年可用性需达到 99.9%，每月停机不能超过 43.8 分钟；  
  - [示例] 重要核心服务 (支付、库存) 要求 99.99% 可用。

- **2.2 故障恢复目标**  
  - **RTO (Recovery Time Objective)**: [示例] 故障发生后 15 分钟内必须恢复；  
  - **RPO (Recovery Point Objective)**: [示例] 数据丢失量不能超过 1 分钟。

- **2.3 冗余 & 容灾策略**  
  - [示例] 多可用区部署、双活/多活；  
  - [示例] 每日全量备份 + 实时增量备份。

- **2.4 关键运营时段**  
  - [示例] 白天 8:00 ~ 20:00 为核心营业时间，必须保证高可用；  
  - [示例] 其余时段可接受临时维护/切换。

---

## 3. 安全与合规需求（Security & Compliance Requirements）

- **3.1 数据隐私 / 合规标准**  
  - [示例] 必须符合 GDPR、CCPA，对于欧盟公民数据需提供删除、导出功能；  
  - [示例] 支付模块需符合 PCI-DSS 要求，不存储明文卡号。

- **3.2 数据加密 / 传输安全**  
  - [示例] 所有 HTTP 接口必须使用 TLS/HTTPS；  
  - [示例] 敏感字段 (密码、Token、2FA 秘钥) 必须进行加盐哈希或对称加密。

- **3.3 访问控制 / 鉴权**  
  - [示例] 采用 RBAC/ABAC 模型，对管理员、客服、用户等不同角色设置不同操作权限；  
  - [示例] 支持 2FA (TOTP、短信) 并可由管理员强制开启。

- **3.4 日志审计 / 合规审计**  
  - [示例] 关键操作（支付、退款、权限变更）需审计日志记录操作人、时间、IP 等信息；  
  - [示例] 日志保留至少 180 天，可根据合规要求做匿名化/脱敏。

- **3.5 漏洞与攻击防护**  
  - [示例] 需防范 SQL 注入、XSS、CSRF、DDOS；  
  - [示例] 定期进行第三方渗透测试或安全扫描。

---

## 4. 可维护性、可观测性（Maintainability & Observability）

- **4.1 代码质量 / 文档**  
  - [示例] 关键模块需配备 80%+ 单元测试覆盖率；  
  - [示例] 对外部接口、领域模型做适当文档化 (JavaDoc 或 Markdown)。

- **4.2 日志 & 监控（Observability）**  
  - [示例] 接口级别打点监控、TraceID 追踪，使用 Prometheus / Grafana；  
  - [示例] 前端可集成 Sentry 做错误跟踪，后端使用 ELK 收集日志。

- **4.3 告警策略**  
  - [示例] CPU、内存、响应时间、错误率等超阈值需自动告警；  
  - [示例] 通知渠道：钉钉 / Slack / PagerDuty 等。

- **4.4 配置管理 / 升级**  
  - [示例] 使用配置中心 (Nacos、Apollo) 动态管理；  
  - [示例] 每周一次例行升级，支持灰度发布。

---

## 5. 技术选型偏好或限制

- **5.1 开发语言 & 框架**  
  - [示例] Java 17 + Spring Cloud Alibaba；  
  - [示例] 前端采用 Vue + TypeScript。

- **5.2 部署架构 & 环境**  
  - [示例] Docker 容器化 + Kubernetes，使用阿里云 ACK ；  
  - [示例] Dev/Stage/Prod 三套环境，支持 CI/CD 自动化发布。

- **5.3 数据库 / 缓存**  
  - [示例] MySQL 8 + Redis 6；  
  - [示例] 分库分表策略，主从复制，满足大数据量读写需求。

- **5.4 第三方服务或云服务**  
  - [示例] 对象存储使用 AWS S3 / 阿里云 OSS；  
  - [示例] 消息队列选用 RocketMQ / Kafka。

- **5.5 组织既有平台或工具**  
  - [示例] 公司已有 Jenkins CI 平台，必须接入；  
  - [示例] 域名管理、SSL 证书统一由运维团队提供。

---

## 6. 其他 NFR 需求

- **6.1 可扩展性**  
  - [示例] 模块化微服务架构，便于后续新增功能独立部署；  
  - [示例] 前后端分离，让前端可单独演进。

- **6.2 多语言 / 国际化**  
  - [示例] 支持中文、英文、日文，后台可根据 Accept-Language 返回对应语言；  
  - [示例] 全局时区设置，日志记录 UTC 时间。

- **6.3 多租户 / SaaS**  
  - [示例] 不同租户数据隔离，可定制子域名和登录策略；  
  - [示例] 能承受 1000 万 DAU，峰值并发需可弹性扩容。

- **6.4 兼容性 / 硬件需求**  
  - [示例] 必须在 Linux x86_64 / Windows Server 等主流平台下稳定运行；  
  - [示例] 前端兼容 Chrome / Firefox / Edge 最新两个版本。

**如何使用此模板？**  
1. 在需求阶段，由产品、架构师、安全、运维等干系人共同完善各项条目；  
2. 在后续架构设计或技术评审中，确保每条 **NFR** 都有相应的方案或验证；  
3. 将此 NFR 文档保持活更新：新出现的安全合规/性能指标等可以在此处做记录并联动任务或测试用例。
