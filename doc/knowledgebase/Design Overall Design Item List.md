## 【一】DDD 战略设计 (Strategic Design)

**目标**：明确业务架构，划分业务边界，保证系统高内聚、低耦合。

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **核心域 (Core Domain)** | 识别业务核心竞争力，重点投入资源 | 业务需求、用户故事 | 关键业务功能/模块 |
| **支撑子域 (Supporting Subdomain)** | 支撑核心业务，但非核心竞争力 | 业务流程 | 辅助功能模块 |
| **通用子域 (Generic Subdomain)** | 通用功能，可复用 | 企业统一需求 | 通用组件 (认证、支付) |
| **限界上下文 (Bounded Context)** | 划分业务逻辑边界，确保模块独立性 | 业务流程、用户故事 | 微服务/模块划分 |
| **上下文映射 (Context Mapping)** | 说明上下文之间如何交互 | 数据流、业务流程 | 上下文关系图/协作模式 |
| **防腐层 (ACL)** | 保护上下文，避免外部系统污染内部模型 | 外部系统 API | 适配后的领域模型 |
| **统一语言 (Ubiquitous Language)** | 业务人员与技术团队共用术语 | 业务术语、用户故事 | 共享术语库 |

**主要产出**：
- 业务核心域、支撑子域、通用子域的划分
- 每个限界上下文的职责与边界
- 上下文映射图 (各微服务交互关系)
- 统一语言 (业务与技术一致)

## 【二】DDD 战术设计 (Tactical Design)

**目标**：基于战略设计划定的业务边界，进一步细化领域模型、编写业务逻辑代码。

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **实体 (Entity)** | 具有唯一 ID 的业务对象，管理业务状态 | 业务需求、用户故事 | 领域对象 (Order, Customer) |
| **值对象 (Value Object)** | 无唯一 ID，不可变，封装业务属性 | 业务规则 | 领域对象 (Money, Address) |
| **聚合 (Aggregate)** | 组合多个实体，维护数据一致性 | 业务规则、实体 | 业务逻辑封装 (OrderAggregate) |
| **聚合根 (Aggregate Root)** | 管理聚合内部对象的一致性 | 聚合、业务流程 | 聚合操作接口 |
| **领域服务 (Domain Service)** | 处理跨聚合的复杂业务逻辑 | 业务规则、实体 | 业务计算/规则封装 |
| **领域事件 (Domain Event)** | 代表业务状态变化，解耦业务逻辑 | 业务事件、状态变化 | 事件消息 (OrderPaidEvent) |
| **应用服务 (Application Service)** | 负责业务流程编排，调用领域层 | 用户请求、API调用 | 领域操作 (CreateOrder, PayOrder) |
| **仓储 (Repository)** | 负责数据存取，保持领域模型纯粹 | 领域对象 | 数据持久化 (数据库) |

**主要产出**：
- 完整领域模型 (实体、值对象、聚合)
- 应用服务 (负责操作编排)
- 领域服务 (跨聚合业务逻辑)
- 领域事件 (事件驱动、消息解耦)
- 仓储接口 (数据持久化策略)

## 【三】API 设计 (API Design)

**目标**：确保微服务之间、前端与后端之间，以及其他外部系统的交互接口清晰、稳定、安全。

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **API 规范 (REST/GraphQL/gRPC)** | 定义服务接口与调用方式 | 领域模型、业务需求 | API 文档 (Swagger, OpenAPI) |
| **API 网关 (Gateway)** | 统一路由、身份认证、负载均衡 | 微服务列表 | 网关路由配置 |
| **身份认证 & 授权 (Auth)** | 确保访问安全 | 安全需求 (OAuth2, JWT) | 安全令牌、认证机制 |
| **版本管理 (API Versioning)** | 兼容旧版 API，同时迭代升级 | API 演进策略 | v1, v2 等版本命名规则 |

**主要产出**：
- API 文档 (Swagger/OpenAPI)
- API 网关配置 (Kong, Nginx, AWS API Gateway)
- 身份认证 & 授权方案 (JWT, OAuth2)
- 版本管理策略 (URL 版本或 Header 版本)

## 【四】系统架构 (NFR) (System Architecture & NFR)

**目标**：满足非功能性需求，如性能、可扩展性、高可用、安全性、部署与运维、数据治理等。

**4.1 性能与可扩展性**

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **缓存 (Caching)** | 提高读取性能、减轻数据库压力 | 业务需求、热点数据 | Redis, Memcached 策略 |
| **CQRS** | 读写分离，提高吞吐量 | 业务查询场景 | 多数据源 (读库 + 写库) |
| **负载均衡 (Load Balancing)** | 分散流量，提升可用性 | 微服务列表 | Nginx, HAProxy 配置 |
| **自动伸缩 (Auto Scaling)** | 动态扩容，适应高并发 | 负载 & 指标 | K8s HPA, AWS ASG |

**4.2 数据架构 (Data Architecture)**

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **数据库选型 (SQL/NoSQL)** | 选择最佳数据库 | 业务需求, 事务/查询场景 | MySQL, PostgreSQL, MongoDB 等 |
| **表结构设计 (DB Schema)** | 设计数据表 & 关系 | 领域模型 | SQL DDL, ER 图 |
| **数据索引 (Indexing)** | 提升查询性能 | 查询模式 | B-Tree, Hash 索引等 |
| **分片 & 读写分离 (Sharding & Replication)** | 提升扩展能力 | 数据量增长预期 | 分布式数据库架构 |
| **数据缓存 (Data Caching)** | 减少数据库访问，提升性能 | 热点数据 | Redis, Memcached |

**4.2.6 数据治理 & 合规 (Data Governance & Compliance)**
- **数据质量 (Data Quality)**：去重、校验、数据清洗
- **元数据管理 (Metadata Management)**：维护数据字典、血缘关系
- **数据生命周期管理 (Retention, Archival)**：数据的产生、归档与删除
- **合规 (GDPR/CCPA 等)**：个人隐私、数据留存/删除策略、脱敏
- 与 **4.5 安全设计** 协同，例如传输加密、审计、访问控制

**4.3 部署架构 (Deployment Architecture)**

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **CI/CD (持续集成 & 持续部署)** | 自动化构建、测试、部署 | 代码仓库 (GitHub, GitLab) | Pipeline (Jenkins, GitHub Actions) |
| **容器化 (Containerization)** | 部署一致性 & 可扩展 | 应用依赖 | Docker 镜像 |
| **编排 (Orchestration)** | 负载均衡、服务编排 | 微服务 | Kubernetes (K8s) 配置 |
| **环境管理 (Env Management)** | 多环境 (Dev, Staging, Prod) 区隔 | 部署策略 | 配置中心 (Consul, Vault) |

**4.3.x 灾备与业务连续性 (DR & BCP)**
- **多机房/多活**：Active-Active / Active-Passive
- **数据备份**：RPO/RTO 指标、定时备份策略
- **故障切换/回切**：Failover / Failback 流程
- **应急演练**：自动化恢复、Chaos Engineering
- **业务连续性预案**：关键服务恢复顺序、人员联动机制

**4.4 运维监控 (Observability & Operations)**

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **日志 (Logging)** | 记录系统运行状态 | 应用日志 | ELK (Elasticsearch + Logstash + Kibana) |
| **监控 (Monitoring)** | 监控各项指标 (CPU, Memory, Request) | 服务器/容器数据 | Prometheus / Grafana |
| **告警 (Alerting)** | 及时发现故障并通知 | 监控指标 | AlertManager, 企业微信/钉钉报警 |
| **分布式链路追踪 (Tracing)** | 排查调用链瓶颈 | 请求数据 | Jaeger, Zipkin |
| **自动故障恢复 (Auto Healing)** | 保证服务高可用 | 运行状态 | K8s 自愈 (重启容器) |

**4.5 安全设计 (Security Architecture)**

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **身份认证与授权 (Auth & Authorization)** | 确保用户或服务正确鉴别、避免越权访问 | OAuth2、JWT、RBAC/ABAC 等策略 | 令牌、权限模型、角色管理等 |
| **数据加密 (Encryption)** | 防止数据在传输或存储时被截获或篡改 | TLS、HTTPS、AES、RSA 等 | 安全的数据传输通道、加密存储 |
| **API 安全 (API Security)** | 保护接口免受恶意攻击、注入或绕过 | Rate Limit、CSRF、XSS 等威胁 | 安全网关配置、跨域策略、防护中间件 |
| **安全审计 (Security Audit)** | 记录并追踪重要操作，满足合规要求 | 合规需求 (GDPR、PCI-DSS 等) | 审计日志、访问日志、异常报警 |
| **零信任架构 (Zero Trust)** | 不再默认信任内部网络，统一强认证策略 | 企业网络环境、访问控制策略 | 零信任网络架构(客户端安全认证、网络隔离) |

> 若合规还有更多安全维度需求，可在此章节加小节 "4.5.x Compliance"，与 4.2.6 的数据合规相互衔接。

**4.6 第三方集成设计 (Integration Architecture)**

**目标**：描述系统与外部服务/第三方平台的交互方式，保障集成的可用性、安全性、可扩展性。

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **集成方式 (Integration Method)** | 明确如何与第三方交互（同步/异步、API/消息等） | 外部系统规格 (API、SDK) | 同步调用方案 / 事件驱动方案等 |
| **防腐层 (ACL) / 适配层** | 适配外部系统数据模型，保护内部领域模型 | 第三方系统接口定义 | 适配器类、DTO 转换、集成封装 |
| **错误重试 & 补偿机制** | 处理失败场景，保证集成一致性 | 异常处理策略 | 重试策略、补偿或回滚流程 |
| **集成安全** | 保证外部交互的安全性，如签名、加密、授权 | 第三方鉴权规则 | Access Token、API 签名、HTTPS 连接 |
| **熔断/限流 (Circuit Breaker / Rate Limit)** | 防止第三方故障蔓延，保护系统 | 依赖第三方可用性 | 熔断策略配置、限流阈值设置 |
| **监控 & 日志** | 对第三方集成调用进行可观测性管理 | 日志 & 监控需求 | 集成调用日志、监控告警(失败率、时延) |

**主要产出**：
- 与每个外部系统/第三方平台的交互方式说明
- 防腐层（ACL）设计与数据适配规则
- 重试/补偿机制
- 安全策略（签名、加密、授权）
- 熔断/限流配置，防止外部故障蔓延
- 第三方接口的日志、监控与告警方案

**4.7 技术栈设计 (Technology Stack)**

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **后端框架选型** | 选择合适的后端开发框架和中间件 | 业务需求、性能要求、团队技术栈 | Spring Boot/Cloud、Node.js、Go等框架选型方案 |
| **前端框架选型** | 选择合适的前端开发框架和UI库 | UI/UX需求、性能要求、团队技术栈 | React/Vue/Angular等框架选型方案 |
| **开发规范** | 统一开发规范和最佳实践 | 框架特性、团队习惯 | 编码规范、项目结构规范、Git规范等 |
| **脚手架工具** | 提供项目初始化和开发工具链 | 开发框架、项目需求 | 项目模板、构建工具、开发工具链 |

**主要产出**：
- 前后端技术栈选型报告
- 开发框架配置方案
- 项目工程化规范
- 开发工具链设计

## 【五】前端设计 (UI & UX)

**目标**：确保用户有良好的交互体验，界面一致、风格统一，并体现业务价值。

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **信息架构 (Information Architecture)** | 规划界面信息层次、导航结构，帮助用户高效查找与操作 | 业务流程、产品需求 | 页面结构草图、导航菜单 |
| **用户流程 (User Flow)** | 描述用户从进入系统到完成某项任务的交互流程 | 用户场景、用户故事 | 流程图或低保真原型 |
| **视觉设计 (Visual Design)** | UI 规范（颜色、字体、图标），统一界面风格 | 品牌指南、主题风格 | 设计稿、UI 组件库 (Figma、Sketch 等) |
| **交互设计 (Interaction Design)** | 定义交互细节（点击、悬停、动画），提高可用性、可访问性 | 可用性标准（WCAG 等） | 原型交互 Demo，高保真原型 |
| **前端技术栈** (React、Vue 等) | 落实到具体框架，实现与后端的 API 调用 | 前端需求、API 文档 | 前端项目结构、代码实现 |

**主要产出**：
- 原型图、UI 设计规范（颜色、排版、组件库）
- 前端技术选型与项目结构
- 用户流程 & 信息架构文档
- 可用性测试与改进建议

## 【六】测试设计 (Test Strategy & QA)

**目标**：保障系统质量和业务逻辑正确性，防止回归故障，提升系统稳定性。

| **概念** | **作用** | **输入** | **输出** |
|---|---|---|---|
| **单元测试 (Unit Test)** | 测试单个模块或函数的行为，保证领域逻辑正确 | 代码、领域模型 | 测试用例、测试脚本 (Jest、JUnit) |
| **契约测试 (Contract Test)** | 测试服务提供者与调用者之间的接口契约，避免集成冲突 | API 规格、依赖服务接口 | 契约测试脚本、测试报告 |
| **集成测试 (Integration Test)** | 测试多个模块协同工作，检查端到端业务流程完整性 | 微服务 API、数据库 | 测试脚本 (Postman, Newman 等)，集成测试报告 |
| **端到端测试 (E2E Test)** | 模拟真实用户操作场景，从前端到后端的完整功能验证 | 前端页面、API、业务数据 | E2E 测试脚本 (Cypress、Selenium) & 报告 |
| **非功能性测试 (Performance, Security)** | 性能、负载、压力、安全等测试 | 系统设计 (NFR) | 压测报告 (JMeter, Locust)、安全扫描报告 (OWASP Zap) |

**主要产出**：
- 测试用例与测试脚本
- 单元测试与集成测试的覆盖率报告
- 性能测试与安全测试报告
- 自动化测试在 CI/CD 中的集成
